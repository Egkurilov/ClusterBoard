# ClusterBoard — спецификация серверного API и SQLite

**Версия контракта:** 1.0. **Дата:** 2026-11-09. **Статус:** проект для последующей реализации, не работающий бэкенд.

Документ описывает серверную часть для существующего портала: «Люди и команды», «Цели квартала», «Инициативы», включая карту кластера, перераспределение, продукты, совместные цели, презентации и Гант. Интерфейс не нужно перепроектировать. Нужно заменить локальное хранение серверным API и добавить вход, состояния запросов и разрешение конфликтов.

**База — обычный SQLite.** Один сервер приложения и один файл базы на локальном постоянном диске. Микросервисы, Redis, Kafka, WebSocket и отдельная графовая база для первого выпуска не нужны.

> Важное ограничение: добавление этого документа не подключает портал к серверу. Пока адаптер API не реализован, `public/index.html` продолжает хранить данные в браузере. Нельзя объявлять приложение многопользовательским только потому, что рядом запущен HTTP-сервис.

## 1. Основание и границы

### 1.1. Проверенный исходный код

Спецификация составлена по `public/index.html` из `Egkurilov/ClusterBoard`, версия интерфейса **0.11**:

- Git blob SHA: `be9b9fd3d16a8377b3e78b91d3ef16e526d7f84a`.
- SHA-256 HTML: `d5b25ef6fb8c27d71f5e2625636ccb60fa263d741a7cbbb3f1d779a2bf684968`.
- Локальный ключ бизнес-данных: `clusterboard-functional-demo-v03`.
- Экспорт прототипа: `format = ClusterBoardPrototype`, `version = 3`.
- Код содержит последовательные переопределения функций. При интеграции проверять окончательное поведение, а не только первое объявление `save`, `gAssign`, `managerOf`, `exportJSON` и других функций.

Подтверждённая модель: `current`, `future`, `people`, `disciplines`, `templates`, `archive`, `goals`, `goalEvents`, `transferEvents`, `initiatives`, `initiativeSettings`; продукты находятся **внутри версии структуры**. Локальные `history` и `goalUndo` — механизмы отмены прототипа, не серверный аудит.

### 1.2. Обязательный объём

Сервер должен обеспечивать:

- Единую базу для компьютера и телефона; вход и серверную проверку прав.
- Полный цикл текущей/будущей структуры, публикацию, архив, восстановление в новый план и сравнение.
- Людей, роли, фиксированные места, руководителей, проценты участия, обязанности, функциональные связи и взаимодействия.
- Продукты нескольких команд и нескольких владельцев с областями ответственности.
- Цели с одним ответственным, несколькими исполнителями, ДОП-признаком и общим прогрессом.
- Инициативы, даты, обновления, системы, историю переносов срока, реестр, доску и данные для Ганта.
- Безопасный импорт существующего JSON, экспорт, аудит, конфликты, резервное копирование и восстановление.

**Не входит в первый выпуск:** SSO, внешние трекеры, почтовые уведомления, файлы-вложения, индивидуальные подзадачи общей цели, критический путь, автоматическое планирование ресурсов, публичные ссылки на презентации, совместное редактирование текста в реальном времени, офлайн-запись с последующим слиянием.

Одна инсталляция первоначально обслуживает один кластер. В данных есть `workspaceId`, чтобы отделять организационную область и права. Это не требование строить многопользовательский SaaS с биллингом.

## 2. Архитектура и ответственность

```text
Safari / Chrome / мобильный браузер
                  |
                HTTPS
                  |
         reverse proxy (same origin)
             /              /api/v1
     статический фронтенд    приложение API
                                  |
                       SQLite на локальном volume
                                  |
                         защищённые резервные копии
```

Фреймворк бэкенда не фиксируется. Подойдёт один модульный сервис с HTTP-обработчиками, прикладными командами, валидаторами и репозиториями SQLite. Контракт не зависит от Python, Node.js или конкретного ORM.

Сервер — единственный источник бизнес-данных. Клиент отвечает за раскладку карты, линии, масштаб, сворачивание, диалоги, видимые ошибки и несохранённые формы. Сервер повторно проверяет все инварианты независимо от клиентской валидации.

Не отправлять клиенту SQL. Не открывать файл базы через HTTP. Не отдавать содержимое `data/`, бэкапы, сессии и конфигурацию как статику.

| Ответственность | Владелец |
|---|---|
| Приёмка правил, публикация оргструктуры, решение по перегрузке | Администратор кластера; первоначально Егор |
| API, транзакции, миграции, аудит | Разработчик бэкенда |
| Замена локальных мутаций, формы, конфликты | Разработчик фронтенда |
| Volume, TLS, бэкапы, восстановление, обновления | Оператор сервиса |

До промышленного запуска у каждой технической ответственности должен быть назначенный человек; документ не назначает вымышленных исполнителей.

## 3. Общие правила API

### 3.1. Формат и адресация

База: `/api/v1`. Все бизнес-маршруты имеют префикс `/workspaces/{workspaceId}`. Далее он сокращён до **`W`**. Идентификаторы — непрозрачные строки до 128 символов. Сервер создаёт новые UUID; старые идентификаторы сохраняются при импорте после проверки уникальности. ФИО, имя команды и код инициативы не являются первичными ключами.

JSON использует `camelCase`. Даты — `YYYY-MM-DD`, моменты времени — UTC RFC 3339, например `2026-11-09T12:30:00Z`. Числовые ревизии — положительные целые. Отсутствующая ссылка — `null`, коллекция — `[]`, словарь — `{}`. Пустые даты прототипа `""` адаптер преобразует в `null` и обратно при legacy-экспорте.

`workspace.timezone` — обязательная IANA-зона, задаваемая администратором при инициализации. Сервер возвращает `today` в этой зоне. Не выводить её из IP, часового пояса телефона или часового пояса контейнера. Календарные даты не превращать в локальные полуночи с последующим сдвигом UTC.

### 3.2. Успешные ответы

Одна сущность:

```json
{
  "data": {"id": "goal_17", "revision": 6, "title": "Подготовить релиз"},
  "meta": {
    "requestId": "req_123",
    "serverTime": "2026-11-09T12:30:00Z",
    "workspaceRevision": 42,
    "changeCursor": "epoch_1:815"
  }
}
```

Список: `data.items`, `data.nextCursor` и `data.total`. По умолчанию `limit=50`, максимум 200; сервер не обрезает списки молча. `total` считается по всему отфильтрованному набору, не по текущей странице. Сортировка стабильная: выбранное поле плюс `id`. Курсор связывается с фильтром и сортировкой. При запросах нескольких страниц клиент получает номер среза; если он устарел, начинает чтение заново.

Специальные проекции карты и Ганта имеют отдельные лимиты, описанные ниже. Бизнес-ответы: `Cache-Control: private, no-store`. Статика и `version.json` имеют самостоятельную политику кэширования.

### 3.3. Мутации и конфликты

Для изменения существующей сущности обязателен **`expectedRevision`**. Пример:

```http
PATCH /api/v1/workspaces/ws_1/goals/goal_17
Content-Type: application/json
X-CSRF-Token: <token>
Idempotency-Key: <random-per-operation>
```

```json
{
  "expectedRevision": 6,
  "changes": {"progress": 70, "status": "on_track"},
  "comment": "Проверены основные сценарии; осталась нагрузочная проверка."
}
```

`PATCH` изменяет только переданные поля; `null` явно очищает разрешённое nullable-поле. Массив заменяется целиком, а не дополняется неявно. Неизвестные поля отклоняются, а не записываются через mass assignment.

При изменениях структуры ожидается **ревизия всего будущего плана**, а не отдельной карточки. Для людей, целей, инициатив, справочников — ревизия соответствующего агрегата. `updatedAt` не используется как средство защиты от гонок.

Внутри короткой транзакции сервер сравнивает ревизию, проверяет права и инварианты, изменяет данные, увеличивает ревизии, пишет аудит и change-feed. Ответ «сохранено» отправляется только после успешного `COMMIT`. У любого бизнес-изменения также увеличивается `workspace.revision`; служебное продление сессии или аренды её не меняет.

Ошибка конфликта не разрешается стратегией «последний победил». Фронтенд сохраняет введённый черновик, загружает актуальную запись и предлагает сравнить/повторить изменение.

### 3.4. Идемпотентность

`Idempotency-Key` обязателен для всех бизнес-мутаций, включая создание, PATCH, назначения, переносы, публикацию, отмену и импорт. Исключения: login/logout, CSRF, просмотр и управление короткой арендой.

Ключ ограничен областью `(workspaceId, userId, dataEpoch, method, canonicalPath, key)`. Хешируется каноническое тело запроса. Повтор с тем же телом возвращает первоначальные статус, результат и `operationId`; с другим телом — `409 IDEMPOTENCY_KEY_REUSED`. Проверка уже завершённой операции происходит до проверки ожидаемой ревизии, но после аутентификации и прав. Поэтому повтор после потери ответа не становится ложным конфликтом.

Успешный ответ и изменения записываются в одной транзакции. Ключи хранятся минимум 7 суток; срок опубликован в `/meta`. Одновременные одинаковые запросы не выполняются дважды. Клиент повторяет сетевой запрос с тем же ключом; осознанно исправленная операция получает новый.

### 3.5. Ошибки

```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "Исправьте обязательные поля.",
    "requestId": "req_124",
    "fieldErrors": [
      {"path": "changes.itOwnerId", "code": "required", "message": "Выберите ответственного от ИТ."},
      {"path": "changes.deadline", "code": "required", "message": "Укажите срок реализации."}
    ],
    "details": {}
  }
}
```

| HTTP | Коды и смысл |
|---|---|
| 400 | `MALFORMED_JSON`, `INVALID_QUERY`, неверный курсор |
| 401 | `AUTH_REQUIRED`, `SESSION_EXPIRED` |
| 403 | `FORBIDDEN`, `CSRF_FAILED` |
| 404 | `NOT_FOUND`; также отсутствие доступа к чужой области |
| 409 | `REVISION_CONFLICT`, `SLOT_OCCUPIED`, `DRAFT_EXISTS`, `ENTITY_IN_USE`, `PLAN_STALE`, `IDEMPOTENCY_KEY_REUSED` |
| 410 | `CURSOR_EXPIRED`, `PREVIEW_EXPIRED`; требуется новое чтение/предпросмотр |
| 413 | `PAYLOAD_TOO_LARGE` |
| 422 | `VALIDATION_FAILED`, `HIERARCHY_CYCLE`, `UNASSIGNED_OWNER`, `INVALID_TRANSITION` |
| 423 | `EDIT_LEASE_HELD`, `EDIT_LEASE_EXPIRED` |
| 428 | `REVISION_REQUIRED` |
| 429 | `RATE_LIMITED`, с `Retry-After` |
| 503 | `DATABASE_BUSY`, `STORAGE_UNAVAILABLE`, `MAINTENANCE`; без SQL и путей на диске |

Для `REVISION_CONFLICT` возвращаются `expectedRevision`, `actualRevision` и ссылка на актуальную сущность. Для `ENTITY_IN_USE` — типы и идентификаторы мешающих ссылок. Возвращать все доступные ошибки формы одним ответом, а не по одной.

### 3.6. Общие лимиты

Обычный JSON-запрос: до 256 KiB; импорт: до 15 MiB после распаковки HTTP-тела; количество элементов проверяется дополнительно. Импорт принимает только JSON, не ZIP и не SQLite-файл. Имена людей — 1–120 символов, названия команды/стрима/продукта — 1–160, цель/инициатива — 1–240. Для остальных полей лимиты указаны в DTO. Проверяется длина Unicode-строки, а не размер UTF-8 вместо количества символов.

## 4. Вход и права

Пользователь приложения и сотрудник — разные сущности. У сотрудника может не быть учётной записи. Связь `user.personId` необязательна. Назначение человеком-владельцем цели не выдаёт права на API автоматически.

Роли в области: `admin`, `editor`, `viewer`. Первоначально создаётся один `admin`. Учётные записи создаёт администратор; публичной регистрации нет.

| Действие | viewer | editor | admin |
|---|---|---|---|
| Читать, искать, показывать карту/Гант | Да | Да | Да |
| Редактировать людей, цели, инициативы | Нет | Да | Да |
| Редактировать будущую структуру при аренде | Нет | Да | Да |
| Публиковать, отбрасывать план, принимать предупреждения | Нет | Нет | Да |
| Полный импорт/экспорт, бэкапы, пользователи | Нет | Нет | Да |
| CSV текущего среза | Нет | Да | Да |

Права не зависят от выбранного цвета раздела или наличия кнопки в браузере. Ограничение редактора своим стримом — отдельное будущее расширение, не скрытое правило первого выпуска.

Сессия — непрозрачный случайный секрет в `HttpOnly; Secure; SameSite=Lax` cookie с `Path=/`, без `Domain`; рекомендуемое имя `__Host-cb_session`. На сервере хранится хеш секрета, не сам секрет. Пароли — Argon2id с параметрами не ниже актуальных рекомендаций OWASP; не собственная криптография [S5, S6]. Для изменяющих запросов обязателен CSRF-токен плюс проверка Origin; SameSite не заменяет CSRF [S7]. Нет токенов входа в `localStorage`, URL и логах.

Предлагаемые настройки: бездействие 12 часов, абсолютная сессия 7 суток, настраиваются оператором. Смена пароля, отключение пользователя и изменение критичных прав отзывают сессии. После возобновления телефона клиент сначала проверяет сессию; при 401 сохраняет несохранённую форму в памяти, но не пишет её анонимно.

| Метод и путь | Контракт |
|---|---|
| `GET /api/v1/auth/csrf` | Создать ограниченную pre-auth сессию или вернуть токен текущей; `data.csrfToken` |
| `POST /api/v1/auth/login` | `{login,password}` + CSRF/Origin; смена идентификатора сессии; ответ UserDto и workspace memberships |
| `GET /api/v1/auth/me` | UserDto, доступные workspace, права, CSRF-токен |
| `POST /api/v1/auth/logout` | Отозвать сессию, очистить cookie; 204 |
| `POST /api/v1/auth/password` | `{currentPassword,newPassword}`; отозвать другие сессии, обновить текущую |
| `GET/POST W/users` | Список / создание учётной записи и membership; только admin |
| `PATCH W/users/{id}` | `expectedRevision`, `changes:{displayName,role,disabled,personId}`; нельзя отключить/понизить последнего admin |
| `POST W/users/{id}/reset-password` | Admin, новый временный пароль, `expectedRevision`; принудительная смена, секрет не входит в аудит/идемпотентный ответ |

`UserDto = {id, login, displayName, personId, role, disabled, mustChangePassword, revision}`. Парольные хеши не сериализуются. Первый admin создаётся CLI-командой с интерактивным вводом или секретом окружения, не дефолтным паролем. Сброс пароля — исключение из сохранения тела ответа идемпотентности: хранится только результат без секрета.

## 5. Загрузка и синхронизация

### 5.1. Bootstrap

`GET W/bootstrap?structure=current&quarter=2026-Q4`

Один согласованный read-срез: metadata workspace, права, `currentVersionId`, `draftVersionId`, ревизии, `directoryRevision`, справочники, карта выбранной структуры и список людей. Цели — выбранный квартал с явной пагинацией; инициативы — первая страница и общая сводка. Полный аудит в bootstrap не включается.

```json
{
  "data": {
    "workspace": {"id":"ws_1","name":"Кластер","timezone":"Europe/Moscow","revision":42,"dataEpoch":"epoch_1"},
    "today":"2026-11-09",
    "versions":{"currentId":"sv_10","draftId":"sv_11"},
    "directoryRevision":7,
    "people":[],
    "disciplines":[],
    "responsibilityTemplates":[],
    "structure":{"id":"sv_10","revision":1,"state":"current","snapshot":{}},
    "goals":{"items":[],"nextCursor":null,"total":0},
    "initiatives":{"items":[],"nextCursor":null,"total":0},
    "capabilities":{"canPublish":true,"canImport":true,"canEdit":true}
  },
  "meta":{"changeCursor":"epoch_1:815"}
}
```

Здесь пустые коллекции и `snapshot:{}` сокращают пример, а не означают разрешение отдавать неполную структуру. Полный SnapshotDto определён в разделе 8.

Первый серверный запуск не создаёт демоданные автоматически. Пустая база показывает «Создать кластер / Импортировать JSON». Недоступность API не включает скрытый fallback к локальной демобазе.

### 5.2. Обновления между устройствами

`GET W/changes?after=epoch_1:815&limit=200` возвращает `items:[{sequence,entityType,entityId,versionId,revision,action,at}]`, `nextCursor`, `hasMore`. Это сигнал перечитать затронутые сущности, не передача всего аудита или персональных данных.

Опрос каждые 15 секунд только в активной вкладке; немедленный опрос после `visibilitychange`, восстановления сети и завершения login. Этот период — настройка первого выпуска, не гарантия мгновенной синхронизации.

Курсор обозначает **последнее доставленное событие**, а не последнюю запись базы, когда есть ещё страницы. Чтение и начальный cursor bootstrap согласованы одной транзакцией. Истечение срока change-feed или новый `dataEpoch` после восстановления дают 410: клиент перечитывает bootstrap.

При открытой изменённой форме автоматическая перезапись её полей запрещена. Показать «Запись обновлена другим пользователем» и сохранить локальный ввод. Презентация фиксирует набор и значения на момент старта; новые данные обозначаются индикатором с явной кнопкой обновления. Масштаб, прокрутка и поля не скачут из-за polling.

## 6. Люди и справочники

### 6.1. PersonDto

`{id, name, active, revision, createdAt, updatedAt}`. ФИО не уникально: однофамильцы допустимы. Переименование не создаёт нового сотрудника и не меняет ссылки.

| Метод и путь | Назначение |
|---|---|
| `GET W/people?q=&versionId=&streamId=&teamId=&active=true` | Поиск по ФИО, роли, команде; стабильная пагинация |
| `POST W/people` | `{name}`; доступно независимо от выбранной версии структуры |
| `GET W/people/{id}` | PersonDto |
| `PATCH W/people/{id}` | `{expectedRevision,changes:{name},comment}` |
| `GET W/people/{id}/overview?versionId=&quarter=` | Назначения и FTE выбранной версии, продукты, цели, инициативы; у каждой коллекции `total/nextCursor` |
| `POST W/people/{id}/deactivate` | `expectedRevision`, комментарий, проверки ссылок |
| `POST W/people/{id}/reactivate` | `expectedRevision`, комментарий |

Деактивация отклоняется, если человек назначен на позицию текущей/будущей структуры, владеет активным продуктом, участвует в незакрытой цели или отвечает за незакрытую инициативу. Возвращается список ссылок. Уже завершённые записи и архивные версии сохраняют человека. Физического удаления через UI нет. Отключение аккаунта пользователя не равно деактивации сотрудника.

Поиск регистронезависим для русского и латинского текста. Не полагаться на стандартный SQLite `NOCASE` для всей кириллицы: хранить поисковое поле с согласованной Unicode-нормализацией и case-folding в приложении. Исходное написание сохраняется. SQL-параметры экранируются; выбор сортировки — из allowlist.

### 6.2. Справочники

`GET/POST W/disciplines`, `PATCH W/disciplines/{id}` и `POST .../{id}/archive`: `{id,name,color,archived,revision}`. Начальные значения: разработка, тестирование, аналитика, внедрение, управление, архитектура. Одна основная дисциплина позиции; не дублировать FTE по дополнительным тегам.

`GET/POST W/responsibility-templates`, `PATCH .../{id}`, `POST .../{id}/archive`: `{id,title,archived,revision}`. Базовый набор соответствует `initialTemplates` фронтенда. Изменение шаблона не переписывает уже назначенные обязанности.

`GET W/systems?q=` — подсказки по системам инициатив. Системы — нормализованные текстовые метки, не копии продуктов и не отдельный каталог архитектурных сервисов. Создание неизвестной метки выполняется атомарно при сохранении инициативы. Нет обязательного отдельного похода в справочник перед вводом задачи.

## 7. Версии организационной структуры

### 7.1. Семантика

В области максимум одна `current` и одна `draft`; старые опубликованные версии — `archived`, отброшенный план — `discarded`. `future` в UI означает активную `draft`, а не вторую независимую базу.

Изменяются только черновики. Текущая и архивные версии неизменяемы структурно. Люди и пользовательские учётные записи общие. Продукты, их команды/владельцы и обязанности входят в снимок структуры. Цели и инициативы в снимок **не входят**.

Идентификатор команды, позиции, места или продукта стабилен между версиями. Ключ снимка — `(workspaceId,versionId,entityId)`. Нельзя переносить ссылку на произвольный объект из другого снимка.

### 7.2. Маршруты

| Метод и путь | Контракт |
|---|---|
| `GET W/structure-versions` | Метаданные версий: `id,state,revision,baseVersionId,createdAt,publishedAt,note` |
| `GET W/structure-versions/{id}` | Метаданные + полный SnapshotDto |
| `POST W/structure-versions` | `{sourceVersionId,expectedWorkspaceRevision,note}`; копия в новый draft; 409, если draft существует |
| `POST W/structure-versions/{id}/validate` | `{expectedRevision}`; ошибки и предупреждения без записи |
| `GET W/structure-diff?from=&to=` | Типизированные изменения команд, мест, позиций, руководителей, процентов, обязанностей и продуктов |
| `POST W/structure-versions/{id}/publish-preview` | `{expectedRevision,expectedWorkspaceRevision}`; одноразовый план публикации |
| `POST W/structure-versions/{id}/publish` | `{previewToken,expectedRevision,expectedWorkspaceRevision,comment,acceptedWarnings:[]}`; только admin |
| `POST W/structure-versions/{id}/discard` | `{expectedRevision,comment}`; только draft, admin; сохраняет след отброшенного плана |
| `POST W/structure-versions/{id}/restore-as-draft` | `{expectedWorkspaceRevision,comment}`; архив не переписывается; 409 при существующем draft |

В ответах создания/публикации возвращаются новые идентификаторы и ревизии. После публикации следующий draft не создаётся автоматически: фронтенд предлагает «Создать будущий план». Это устраняет неявное редактирование только что опубликованной структуры.

### 7.3. Редактирование по очереди

Для draft используется короткая серверная аренда:

- `POST W/structure-versions/{id}/lease` с `{clientId}` → `{leaseToken,expiresAt,holder}`.
- `POST .../{id}/lease/renew` с `{clientId,leaseToken}`.
- `POST .../{id}/lease/release` с `{clientId,leaseToken}`.
- `POST .../{id}/lease/force-release` — admin, с причиной и аудитом.

TTL 120 секунд, продление раз в 40 секунд активного редактирования. `clientId` уникален для вкладки, а не для человека. Для всех структурных мутаций обязателен `X-Edit-Lease`. В базе хранится хеш токена; чужим клиентам возвращается только владелец/срок. Право на lease проверяется и при приобретении, и в каждой мутации. После потери lease форма не теряет ввод, но сохранение запрещено до повторного получения и сверки ревизии.

Аренда не держит открытую транзакцию SQLite. Она не заменяет `expectedRevision`. Цели и инициативы редактируются с оптимистической проверкой без общей блокировки всего портала.

### 7.4. Публикация

В одной транзакции: проверить аренду, ревизии, неизменность базовой current, права; повторить валидацию; архивировать прежнюю current; присвоить draft состояние current; сохранить подписи справочников на момент публикации; записать аудит; обновить workspace revision.

Ошибки, запрещающие публикацию: циклы, битые ссылки, позиция без места, два назначения на одно место, неверная иерархия, лидер чужого подразделения, одинаковый ID у разных сущностей, отрицательные/недопустимые проценты.

Управленческие предупреждения: нет назначенного лидера/человека, открытая вакансия, сумма участия больше 100%, обязанность без владельца, продукт без владельца, несколько владельцев без разделённых областей. Их можно принять **только явно** с кодами предупреждений, `entityId` и комментарием admin. Нельзя скрыто снижать проценты или автоматически назначать владельца. Это позволяет описывать существующую проблемную реальность, не объявляя её нормальной.

`previewToken` действует 10 минут и связан с хешем плана, всеми проверенными ревизиями и инициатором. Изменение плана или справочника после preview требует нового preview; commit повторяет критические проверки. Изменения целей/инициатив не изменяют структуру и не очищаются публикацией.

## 8. Подразделения, места и позиции

### 8.1. SnapshotDto — проекция для существующей карты

```json
{
  "cluster":{"id":"cluster_1","name":"Платежные решения","desc":"Кластер"},
  "clusterLead":"pos_cluster_lead",
  "streams":[{"id":"s_products","name":"Клиентские продукты","desc":"","tone":"green","leadId":"pos_stream_lead","order":0}],
  "teams":[{"id":"t_web","streamId":"s_products","name":"Web","desc":"","tone":"teal","leadId":"pos_team_lead","order":0}],
  "slots":[{"id":"slot_1","type":"team","container":"t_web","positionId":"pos_1","managerId":null,"order":1}],
  "positions":{
    "pos_1":{"id":"pos_1","slotId":"slot_1","role":"Разработчик","disciplineId":"d_dev","discipline":"Разработка","personId":"person_1","load":60,"description":"","vacant":false,"responsibilities":[],"functional":[],"interactions":[]}
  },
  "products":[]
}
```

Пример частичный: в настоящем снимке все лидеры и ссылки должны существовать. `discipline` — отображаемое имя по `disciplineId`, не отдельный изменяемый справочник. `slot.positionId` вычисляется из связи позиции с местом, а не хранится второй независимой колонкой.

`collapsed`, масштаб, линии, координаты и выделение относятся к UI. Их отсутствие не должно ломать карту. Пространственные координаты на сервере не определяют подчинение.

### 8.2. Единый endpoint команд структуры

Чтобы одно действие пользователя не разбивалось на несогласованные запросы, вложенные изменения проходят через:

`POST W/structure-versions/{versionId}/commands`

```json
{
  "expectedRevision":17,
  "type":"position.update",
  "payload":{"positionId":"pos_1","changes":{"role":"Ведущий разработчик","load":60}},
  "comment":"Уточнение роли"
}
```

Ответ: `{operationId,versionId,revision,snapshot,warnings}` в `data`. Для текущего размера кластера допустимо возвращать весь согласованный snapshot. Команды атомарны, используют lease и один idempotency key. Сервер выбирает обработчик из allowlist; произвольных имён функций, SQL, JSONPath и скриптов нет.

| `type` | `payload` и поведение |
|---|---|
| `cluster.update` | `{changes:{name,desc}}` |
| `stream.create` | `{name,desc,tone,order}`; возвращает ID |
| `stream.update` | `{streamId,changes:{name,desc,tone}}` |
| `stream.remove` | `{streamId}`; только пустой, иначе 409 со ссылками |
| `stream.reorder` | `{orderedIds:[...]}`; ровно все стримы, без дублей |
| `team.create` | `{streamId,name,desc,tone,order}` |
| `team.update` | `{teamId,changes:{name,desc,tone}}` |
| `team.move` | `{teamId,destinationStreamId,order}`; сохраняет состав, продукты и ID; меняется начальник техлида по новым правилам |
| `team.remove` | `{teamId}`; только пустая команда без мест/позиций/привязок продуктов; цели исторически не удаляются |
| `team.reorder` | `{streamId,orderedIds}` |
| `slot.create` | `{type,container,order,managerId:null}`; пустое фиксированное место |
| `slot.update` | `{slotId,changes:{managerId}}`; изменение явного руководителя требует проверки циклов |
| `slot.remove` | `{slotId}`; только пустое место |
| `slot.reorder` | `{type,container,orderedIds}`; все места контейнера, включая пустые |
| `position.create` | `{slotId,role,disciplineId,personId:null,load:100,description:"",vacant:false}`; слот должен быть пуст |
| `position.update` | `{positionId,changes:{role,disciplineId,personId,load,description,vacant}}`; не принимает произвольный `slotId` |
| `position.remove` | `{positionId}`; сохраняет пустое место; запрещено при подчинённых, лидерстве, входящих связях или владении обязанностью |
| `lead.assign` | `{type,container,positionId}`; лидер должен занимать позицию этого контейнера |
| `lead.clear` | `{type,container}`; оставляет явное предупреждение, не выбирает случайную замену |
| `responsibility.*` | Раздел 10 |
| `link.*` | Раздел 10 |
| `product.*` | Раздел 11 |

Удаление из draft не удаляет stable identity, архивные снимки и цели, ссылающиеся на подразделение. Отсутствие в новой current отображается у старой цели как «Команда больше не входит в текущую структуру», а не как исчезновение цели.

### 8.3. Инварианты подчинения

Иерархия подразделений строго `cluster → stream → team`. Все позиции имеют одно место. Один человек может иметь много позиций. Отсутствие `personId` не означает `vacant=true`; при `vacant=true` назначенный человек недопустим.

`load` — целое 1–100 на позицию. Сумма по человеку считается **внутри одной версии**, current и draft не складываются. Выше 100% — управленческое предупреждение. Ниже 100% — «не распределено в этой структуре», а не гарантированно свободное время. Владение продуктом, целью или инициативой FTE не добавляет.

Разрешение административного руководителя:

1. Для лидера кластера — `null`.
2. Если задан `slot.managerId`, использовать его после проверки существования и отсутствия цикла.
3. Для лидера стрима — лидер кластера; для лидера команды — лидер её стрима.
4. Для остальных позиций — лидер их контейнера; для общекластерных позиций — лидер кластера.
5. Если соответствующего лидера нет, вернуть `null` и предупреждение. **Не перепрыгивать к руководителю более высокого уровня молча.** Это осознанное усиление серверного правила относительно fallback старого прототипа; импорт сохраняет прежний эффективный manager явным `slot.managerId`, если это нужно для точного переноса.

Циклы проверяются по окончательному графу после команды, а не только по изменённой карточке. Функциональная связь не меняет административного руководителя.

## 9. Перенос и разделение участия

`POST W/structure-versions/{id}/transfer-preview` — чтение и расчёт последствий. `POST .../{id}/transfers` — применение. Никаких пустых мест и новых людей на preview не создаётся.

```json
{
  "expectedRevision":17,
  "positionId":"pos_1",
  "mode":"move",
  "destinationTeamId":"t_mobile",
  "destination":{"slotId":null,"createSlot":true,"managerId":null},
  "splitLoad":null,
  "successorPositionId":null
}
```

Результат preview: `previewToken`, срок действия, исходная/целевая команда, старый/новый руководитель, проценты до/после, затронутые позиции, незакрытые обязанности, предупреждения. Commit принимает `previewToken`, `expectedRevision`, `comment` и `acceptedWarnings`; сервер повторно проверяет актуальность.

| Режим | Правило |
|---|---|
| `move` | Перенос выбранной позиции; человек, роль, процент, обязанности, функциональные связи и взаимодействия сохраняются. Старый слот остаётся пустым. Другие назначения человека и его цели не меняются. |
| `split` | Только позиция с человеком без подчинённых и не лидер контейнера. `0 < splitLoad < oldLoad`. Исходная нагрузка уменьшается, новая позиция получает ту же персону и роль. Обязанности и связи остаются в исходной позиции; новая получает пустые коллекции. Сумма нагрузки сохраняется. |
| `branch` | Перенос позиции и всех административных потомков. Внутреннее подчинение сохраняется; верхняя позиция получает нового руководителя. Для потомков создаются отдельные слоты, старые остаются пустыми. |

Если переносится руководитель без ветки, обязательна явная замена `successorPositionId`; перенос не может сделать эту замену подчинённой самой себе. Если уходит вся ветка-лидер команды, исходный `leadId=null`; это видно в preview и проверке публикации. Продукты исходной команды автоматически за людьми не переезжают.

Целевая команда и менеджер должны существовать. Занятый слот — 409, перезапись запрещена. Новое место создаётся только в транзакции commit. При `split`, сохранении продукта с новым владельцем и любых других составных операциях частичный успех запрещён.

Отмена переноса — новая проверяемая компенсирующая операция из раздела 16. Нельзя просто восстановить весь старый `data` и затереть изменения других пользователей.

## 10. Ответственность и связи

Каноническая обязанность: `{id,title,scope,templateId:null,ownerPositionId:null,participantPositionIds:[]}` внутри версии. Один владелец результата, сколько угодно участников. `scope` — текст до 240 символов с конкретной областью, а не только «разработка».

Команды `responsibility.create`, `responsibility.update`, `responsibility.remove` принимают объект/изменения с этими полями. Назначение владельца и участников выполняется атомарно; владелец не дублируется участником. Отсутствие владельца допустимо в описываемой структуре как явная проблема; для публикации требует подтверждения предупреждения.

Для совместимости SnapshotDto разворачивает обязанность в каждой позиции как `{id,title,scope,owner:boolean}`. Это проекция одной обязанности, а не независимые дубли.

Связь: `{id,sourcePositionId,targetPositionId,type:"functional"|"interaction",scope,direction:"one_way"|"two_way"}`. `link.create/update/remove` работают с этой сущностью. Для functional обязательна область, направление всегда `one_way`; для interaction подпись описывает смысл. Самоссылка запрещена. Двусторонняя связь хранится один раз; повтор создаёт идемпотентный результат либо 409, но не две линии. Административные связи здесь не хранятся: они вычисляются по местам и лидерам.

`GET W/structure-versions/{id}/responsibilities` возвращает обязанности и флаги `missingOwner`, `crossTeam`, `duplicateScopeCandidates`. Не объединять обязанности автоматически только из-за одинаковых названий.

## 11. Продукты и владельцы

`ProductDto = {id,name,description,teamIds:[],ownerIds:[],ownerScopes:{personId:scope},archived,isDemo}`. Один продукт может обслуживаться несколькими командами. У команды может быть несколько продуктов. Техлид — лидер команды; владелец продукта не становится административным руководителем.

`GET W/structure-versions/{id}/products?teamId=&ownerId=&archived=false&q=` — каталог. `GET .../products/{productId}` — продукт, команды, владельцы и ссылки на связанные цели; цели берутся из независимого раздела, а не из снимка.

Структурные команды:

- `product.create`: `{product:{name,description,teamIds,ownerIds,ownerScopes},newPeople:[]}`.
- `product.update`: `{productId,changes:{name,description,teamIds,ownerIds,ownerScopes}}`.
- `product.archive` / `product.restore`: `{productId}`.

`description` до 2000 символов, scope владельца до 240. Для неархивного продукта нужна минимум одна команда. В draft допускается отсутствие владельцев с предупреждением; несколько владельцев требуют явно указанных областей перед публикацией либо принятия предупреждения admin.

Создание человека в диалоге продукта поддерживается **одним запросом**: `newPeople:[{clientRef:"new-owner-1",name:"..."}]`, а ссылка в `ownerIds` задаётся как `"$new-owner-1"`. Сервер создаёт используемых новых людей и продукт в одной транзакции, возвращает `resolvedPeople:{"new-owner-1":"person_uuid"}`. При ошибке не остаются лишние сотрудники. Для нового человека проверяется обычное право editor на справочник. Одинаковое имя не означает того же человека.

Архивирование продукта не удаляет его из истории и не снимает привязки целей. Архивный продукт нельзя выбрать для новой активной цели, но старые записи продолжают показывать его имя.

### 12.3. Правила сохранения и переходов

Название, квартал и допустимая дата внутри квартала обязательны даже для draft. Для состояний, кроме draft/cancelled, нужны существующий ответственный, существующий стрим и критерий достижения. Команда, когда указана, при новом назначении должна принадлежать выбранному стриму текущей структуры.

Смена состава проходит через один прикладной сервис для PATCH и `/assignments`; нельзя рассогласовать owner, участников и вклад. Если передаётся одно поле из группы `ownerId/participants/contributions`, требуется вся группа. Старый ответственный не добавляется автоматически на сервере: UI по умолчанию включает его в новый массив участников и показывает это перед сохранением.

Добавление drag-and-drop **не меняет ответственного**. Повторное назначение уже назначенному человеку — 200 без дубля, без новой ревизии и события изменения. Цель без owner остаётся draft; назначение только исполнителей не переводит её в работу.

Изменение процента или статуса существующей цели требует непустой `comment`. `done` требует 100% и подтверждения результата. 100% само по себе не переводит в done. `cancelled` требует причины. Возобновление done/cancelled разрешено editor/admin только явно с причиной и повторной валидацией рабочих обязательных полей; drag-and-drop для закрытой цели запрещён.

`progressUpdatedAt` обновляется только при содержательном обновлении выполнения/статуса или `/confirm-current`, а не при переименовании, смене ДОП, состава или стрима. Обычный комментарий может храниться в истории, но не маскирует устаревший статус.

После публикации структуры старые ссылки цели не переписываются. Если подразделение/продукт выбыло из current, цель имеет `referenceWarnings`; обновить её прогресс можно, не теряя историческую принадлежность. При новом назначении или смене этих ссылок выбираются существующие активные сущности. Нельзя внезапно запретить обновление старой цели только потому, что произошла реорганизация.

### 12.4. Подсчёты

Одна цель с тремя людьми — **одна цель, три назначения**. У человека `total`, `owner`, `participant`, `active`, `done`, отдельно основные/ДОП. `total = owner + participant` без двойного учёта одной цели. Общий процент не является личной оценкой каждого участника.

«Без целей» — нет ни одной неотменённой цели выбранного квартала в роли owner или participant, включая завершённые. «Без основных целей» — та же проверка только по `isAdditional=false`. Человек с завершёнными целями не становится «без целей». Область списка сотрудников включает назначения в структуре, владельцев продуктов и явных межстримовых участников; флаг отсутствия целей проверяет весь выбранный квартал, чтобы узкий фильтр не создал ложный вывод.

В сводке показываются `done/total` по основным и ДОП; не вычислять средний прогресс разнородных целей как «выполнение квартала». Количество целей не конвертируется в FTE.

### 13.3. Валидация и актуальность

Вне draft/cancelled нужны ответственный от ИТ, заказчик, deadline и statusText. Для blocked нужен blocker, health принудительно `risk`. Для done нужны 100% и описание результата. Завершение/отмена/возобновление — явные действия с объяснением; процент не меняет статус автоматически.

При изменении уже существующей даты начала или deadline требуется причина. Первое заполнение пустой startDate не требует выдуманной причины, но записывается в аудит. `startDate <= deadline`, если обе заданы. Очистка заданной даты также считается изменением. `baselineDeadline` фиксируется при первом непустом deadline и не меняется ни переносом, ни архивированием.

`statusUpdatedAt` меняется при изменении `status,health,statusText,progress,nextStep,nextStepDate,blocker,decisionNeeded` или явном подтверждении. Переименование, изменение описания/заказчика/систем, срока, владельца или архивирование само по себе не делает обновление свежим. `updatedAt` отражает любую бизнес-правку.

Все состояния, кроме done/cancelled, разрешено изменять друг в друга после проверки обязательных полей. Done/cancelled можно возобновить с причиной. Архив — независимый признак, не статус; архивирование активной инициативы требует подтверждения и комментария, чтобы она не исчезла из контроля незаметно.

Просрочка: неархивная рабочая инициатива, статус не draft/done/cancelled, deadline раньше `today`. Ближайший срок — от today до today+14 включительно. Stale — рабочая инициатива, прошедшее число календарных дней в timezone области не меньше staleDays. MissingOwner отдельно. Все вычисленные флаги возвращает сервер, чтобы телефон и компьютер считали одинаково.

## 14. Гант и презентации

`GET W/initiatives/gantt?from=2026-11-01&to=2027-01-31&groupBy=stream&...filters`

Ответ:

```json
{
  "data": {
    "asOf":"2026-11-09T12:30:00Z",
    "today":"2026-11-09",
    "timezone":"Europe/Moscow",
    "range":{"from":"2026-11-01","to":"2027-01-31"},
    "items":[{"id":"ini_1","title":"Запуск SDK","streamId":"s_products","itOwnerId":"person_1","startDate":"2026-11-02","deadline":"2026-12-20","baselineDeadline":"2026-12-15","progress":60,"status":"in_progress","health":"risk","revision":3}],
    "unscheduled":[{"id":"ini_2","title":"Подготовить регрессию","missingFields":["startDate"]}],
    "totalMatched":2,
    "totalScheduled":1,
    "totalUnscheduled":1,
    "totalOutsideRange":0,
    "truncated":false
  }
}
```

Полоса есть только при корректных обеих датах. Инициативы с одним deadline не исчезают: `unscheduled`. Однодневная задача допустима. В диапазон попадают пересекающиеся периоды, а не только задачи, начинающиеся внутри него: `startDate <= to AND deadline >= from`.

Даты отдавать исходные; обрезка полосы по краю экрана — работа клиента. Период включает оба граничных дня. Масштабы «Вместить / Дни / Недели / Месяцы», геометрия, группировка и линия «Сегодня» — вычисления интерфейса из единого набора. Прогресс не вычисляется по прошедшему времени. Изменения дат перетаскиванием, зависимости и критический путь отсутствуют.

Проекция возвращает до 2000 совпадений, **с учётом unscheduled**, целиком из одного read-среза. При превышении — 422 `VIEW_TOO_LARGE` с total и предложением сузить фильтры; не показывать часть как «все задачи». То же правило у полной карты: до 5000 позиций и всех связанных контейнеров. Это конфигурируемые защитные лимиты, не заявление об измеренной производительности.

### Презентационный срез

`POST W/presentation-snapshots` — read-only операция с body `{kind:"structure"|"initiatives"|"gantt",versionId:null,ids:[],filters:{}}`. Возвращает неизменяемый набор значений, `asOf`, `workspaceRevision`, `today` и источник выборки. Без записи бизнес-данных, без idempotency key; auth и CSRF обязательны для POST. Снимок живёт в памяти клиента; серверу не нужен отдельный генератор PowerPoint или публичная ссылка.

Явные `ids` задают порядок и приоритет над filters; все проверяются по правам, максимум 2000. Для структуры возвращается весь выбранный снимок, а не только текущая видимая ветка. Отказ в доступе хотя бы к одной сущности не должен раскрывать её название. Презентация использует те же DTO, но кнопок записи нет; это не замена серверным правам.

## 15. Сводки и поиск

`GET W/structure-versions/{id}/summary?streamId=&teamId=` возвращает количество стримов, команд, позиций, уникальных людей, сумму FTE, вакансии, незаполненные позиции без пометки вакансии, перегрузки, обязанности без владельца и продукты без владельца. `GET .../map` — полный согласованный SnapshotDto плюс справочник отображаемых имён, без пагинации узлов по умолчанию.

`GET W/search?q=&scope=people|structure|goals|initiatives&versionId=&quarter=` — контекстный поиск; пустой scope или scope вне allowlist дают 400. Результат содержит тип, ID, название, контекст и route для открытия. Не открывать формы с чужими правами только потому, что элемент попал в поиск.

Сводки и списки используют один набор фильтров. Отдельно возвращать `scopeTotals` до применения metric и `filteredTotals` после: нажатие «Требуют внимания» не должно стирать смысл всех остальных счётчиков. Для выборки с несколькими продуктами/исполнителями SQL считает `COUNT(DISTINCT goal_id/person_id)`, а не количество строк JOIN.

## 16. История и отмена

`GET W/audit?entityType=&entityId=&versionId=&actorId=&cursor=` — admin, editor для бизнес-истории своей области. Viewer получает безопасные события конкретной доступной сущности, без технических данных аккаунтов.

Событие: `{id,operationId,actorUserId,actorLabel,action,entityType,entityId,versionId,at,comment,changes:[{path,before,after}],source}`. Actor и время задаёт сервер. Из импортированного события нельзя делать подтверждённое действие текущего пользователя: `source=legacy_import`, исходный автор — отдельный неподтверждённый label.

Аудит append-only на уровне приложения; обычных update/delete endpoints нет. Это не криптографическая защита от администратора файловой системы. В логи не попадают пароли, cookie, CSRF, сырые тела импорта и все персональные поля целиком.

`POST W/operations/{operationId}/undo-preview` и `POST .../undo` поддерживают отмену последних структурных операций и изменений цели. Commit принимает `expectedRevision`, `previewToken`, `comment`, idempotency key; для структуры также lease. Доступна только обратимая операция, после которой затронутые агрегаты не менялись. Иначе 409 с перечнем конфликтов. Отмена — новый audit event и новая ревизия, не удаление истории. Созданного совместно человека нельзя удалить при undo продукта, если уже появились другие ссылки.

Публикация не отменяется переписыванием current; используется `restore-as-draft` с последующей публикацией. Импорт и физическое восстановление не имеют обычной кнопки undo; перед ними нужна резервная копия.

## 17. Импорт и экспорт

### 17.1. Форматы

Поддерживать `ClusterBoardPrototype/version=3`, `uiVersion` как необязательную подсказку. Сохраняются current/future, люди, дисциплины, шаблоны, опубликованный archive, продукты, цели, их назначения/вклад/ДОП, goalEvents, transferEvents, инициативы со всеми датами/системами/events и initiativeSettings. Старый raw localStorage-объект распознаётся явно как legacy без envelope и выводится в отчёте.

Не импортируются auth, локальные prefs, `history`, `goalUndo`, текущая арендная сессия и служебные флаги вкладок. Отчёт перечисляет пропущенные технические поля. Нельзя молча выбросить неизвестные **бизнес**-поля: вернуть предупреждение/ошибку и оставить исходный файл доступным для скачивания.

Новый экспорт: `format=ClusterBoardServerExport`, `schemaVersion=1`, `apiVersion=v1`, `exportedAt`, workspace metadata, стабильные IDs, версии/исторические подписи, бизнес-данные и аудит. Секреты, хеши паролей, сессии, idempotency ledger и lease не входят. Предусмотреть `format=legacy-v3` для переноса в прототип с отчётом полей, которые он не поддерживает. Полный backup базы и бизнес-экспорт — разные продукты.

### 17.2. Двухфазный импорт

1. `POST W/imports/preview` с `{format:"auto",mode:"initialize"|"replace",expectedWorkspaceRevision,payload:{...}}`.
2. Сервер валидирует весь граф, даты, статусы, ID, ссылки, историю, массивы и лимиты; нормализует в staging, но не меняет рабочие данные.
3. Ответ `{planId,sourceSha256,expiresAt,expectedWorkspaceRevision,counts,errors,warnings,idMap,changes}`. Ошибки содержат JSON path.
4. Admin подтверждает: `POST W/imports/{planId}/commit` с `{expectedWorkspaceRevision,confirmation:"REPLACE WORKSPACE",acceptedWarnings:[...],comment}`.
5. Повторно проверить ревизию, актуальность plan, отсутствие активного редакторского lease; создать согласованную резервную копию; в одной транзакции применить бизнес-данные, audit и новый dataEpoch. Отозвать lease и invalidation cursors. Сессии и права не импортировать.

Plan действует 30 минут, доступен только инициатору-admin, связан с хешем payload и режимом. Payload хранить в защищённом staging, удалять после истечения/commit. `initialize` разрешён только для пустой бизнес-области. `replace` — явная полная замена, не попытка угадать merge. Автоматическое объединение данных разных браузеров не входит в v1.

Повтор commit с тем же idempotency key не создаёт вторую замену. Ошибка на любом этапе оставляет прежнюю базу целой. Подготовленная резервная копия помечается исходной ревизией; новый dataEpoch генерируется и при восстановлении из копии, чтобы старые клиенты не писали поверх восстановленной базы.

### 17.3. Нюансы миграции

- Current/future превращаются в отдельные version ID, но IDs вложенных сущностей сохраняются.
- Отсутствующий `isAdditional` → false; `participants` дедублицируются и исключают owner с записью нормализации в отчёте.
- Продукты **не добавляются демомиграцией** на сервере; их отсутствие — допустимые реальные данные.
- Системы инициатив получают Unicode-нормализованные ключи без изменения исходного текста; возможные объединения показываются в preview.
- Позиционные обязанности с разными ID не объединяются по одному title/scope. Возможные дубли — отдельное предупреждение; явный общий ID одной обязанности объединяется с проверкой единственного owner.
- Дробная/невалидная нагрузка, два владельца одной обязанности, битая ссылка или цикл — ошибка, требующая исправления до commit, а не молчаливое округление/удаление.
- Инициатива без startDate остаётся без периода. Не заполнять начало датой создания.
- Неизвестная историческая подпись помечается `historicalLabelUnavailable`; нельзя утверждать, что текущее ФИО было таким же год назад.
- Графически одинаковые, но разные люди не сливаются по ФИО.

`GET W/exports?format=server-v1|legacy-v3&includeAudit=true` выдаёт согласованный JSON-срез admin. `GET W/initiatives/export.csv` экранирует кавычки, переносы и формульные префиксы `=,+,-,@,tab,CR`; CSV не является backup. `POST W/demo-data/preview` и `/commit` разрешены только admin при `ENABLE_DEMO_TOOLS=true`; по умолчанию выключены. Демо-записи помечаются и не заменяют реальные.

## 18. Модель SQLite

Ниже **логическая схема для миграций**, а не готовый SQL-файл. Она определяет связи и ограничения; точный синтаксис DDL и миграции создаются при реализации и проверяются отдельными тестами.

### 18.1. Типы и общие правила

`id/W/V` = TEXT, `revision/sequence` = INTEGER, boolean = INTEGER CHECK IN (0,1), календарные даты = nullable TEXT, timestamps = TEXT UTC. `W` — workspace_id, `V` — version_id. JSON допускается для immutable-снимков, полей аудита, preferences и staging, но не вместо всех доменных таблиц.

Для каждого вложенного объекта обязательны составные FK, учитывающие W и V. Не проверять ссылку только по голому ID из другого workspace. `ON DELETE CASCADE` допустим для вспомогательных строк удаляемого draft-объекта; не для shared people, stable identities, опубликованных версий и аудита. По умолчанию — RESTRICT.

### 18.4. Исторические имена

При публикации сохранить `directory_snapshot_json` с именами связанных людей и отображаемыми названиями дисциплин на момент публикации. Для current/draft интерфейс использует живой справочник, для archived по умолчанию — подписи снимка. Можно явно запросить `labels=live`, не выдавая это за историческую точность.

При архивировании прежней current зафиксировать её последний живой справочник отдельно в metadata архива, если требуется представление «на дату замены». Не перезаписывать опубликованный `directory_snapshot_json`. Это две разные даты и два разных представления, а не скрытая мутация прошлого.

## 19. Транзакции и эксплуатация

### 19.1. Настройки SQLite

SQLite поддерживает одновременно одного писателя; WAL позволяет чтению и записи меньше мешать друг другу, но не превращает SQLite в multi-writer кластер [S1, S2]. Для этого портала выбираем короткие записи и один экземпляр сервиса.

При подготовке базы:

```sql
PRAGMA journal_mode = WAL;
```

Проверить, что результат действительно `wal`. На каждом соединении:

```sql
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;
PRAGMA synchronous = FULL;
```

Не запускать смену journal_mode на каждом HTTP-запросе. Foreign keys включать вне транзакции и проверять при старте [S3]. FULL выбран в пользу сохранности подтверждённых записей; не менять на OFF/NORMAL без отдельного решения по допустимой потере последних изменений [S2].

**Требование к сборке:** использовать поддерживаемый stable SQLite с исправлением WAL-reset, сверяя реальный `SELECT sqlite_version()` внутри runtime. Исправление есть в 3.51.3 и последующих исправленных выпусках; 3.52.0 был отозван. Не считать версию языка/ORM доказательством версии SQLite. Для новой установки предпочтительна актуальная поддерживаемая стабильная сборка не ниже исправленной линии; фиксировать конкретный образ и проверять release notes [S8].

Файл базы, `-wal` и `-shm` — на одном локальном volume того же хоста. Не NFS/SMB, не общая сетевая папка между экземплярами. `data/` не находится внутри `public/` и не добавляется в Git.

### 19.2. Шаблон записи

```text
Проверить аутентификацию, CSRF и права.
Проверить синтаксис/размер запроса вне транзакции.
BEGIN IMMEDIATE.
  Проверить workspace/dataEpoch и текущие права.
  Найти завершённый idempotency record; при совпадении вернуть его после завершения чтения.
  Проверить revision и lease, если требуется.
  Загрузить затронутый агрегат; применить изменения в памяти.
  Проверить все ссылки, переходы и бизнес-инварианты.
  Записать агрегат и увеличить его revision.
  Увеличить workspace.revision; при изменении справочника — directoryRevision.
  Записать audit/change event и данные для безопасной отмены.
  Записать idempotency result с operationId.
COMMIT.
Вернуть успешный ответ.
```

Никаких внешних HTTP-запросов, ожидания пользователя, генерации больших файлов или сна внутри write-транзакции. Нельзя `BEGIN` при открытии формы и держать до нажатия Save. При busy после timeout — rollback и 503 `DATABASE_BUSY`, повтор тем же idempotency key. Не ретраить бесконечно. При ошибке диска/квоты — нет успешного ответа, все данные и аудит либо вместе записаны, либо вместе откатились.

Read-снимки для bootstrap, экспортов и презентаций должны быть согласованы. Результат подготовить в пределах ограниченного чтения, отпустить транзакцию до медленной отправки клиенту: долгий читатель может мешать checkpoint [S2].

### 19.3. Развёртывание

Существующий reverse proxy раздаёт `/` из статики, `/api/` направляет в backend. Backend не публикует SQLite и не слушает Интернет напрямую. Конфигурация будущего сервиса:

```text
DATABASE_PATH=/var/lib/clusterboard/clusterboard.sqlite3
PUBLIC_ORIGIN=https://<domain>
WORKSPACE_TIMEZONE=<IANA timezone>
SESSION_IDLE_SECONDS=43200
SESSION_MAX_SECONDS=604800
SQLITE_BUSY_TIMEOUT_MS=5000
MAX_IMPORT_BYTES=15728640
ENABLE_DEMO_TOOLS=false
BACKUP_DIR=/var/backups/clusterboard
```

`file://` и публичный HTTP-IP не являются production-режимом авторизованного приложения. Нужен HTTPS на настроенном origin; послабление для HTTP допускается только в явно обозначенном local development, не как автоматическое понижение cookie-защиты. Нельзя CORS `*` с credentials. Для same-origin CORS не требуется.

Миграции запускаются однократно до старта HTTP-worker, с checksum и schema_migrations. Несовместимая версия схемы — отказ readiness, не автосброс. При обновлении архивировать прежний образ и сделать проверяемый backup. Не запускать конкурентные миграции из нескольких workers. Начальная конфигурация — один backend instance; несколько соединений допустимы, но запись короткая и конкурентность контролируемая.

### 19.4. Бэкапы и восстановление

Использовать SQLite Online Backup API или другой документированный согласованный способ [S4]. Не копировать только `.sqlite3` у активной WAL-базы: подтверждённые данные могут быть в WAL [S2].

Предлагаемые эксплуатационные цели, требующие подтверждения владельцем: RPO не более 1 часа, RTO не более 1 часа. Часовые копии — 48 часов, ежедневные — 30 дней, еженедельные — 12 недель; минимум одна копия вне основного сервера. Шифрование копий, ограничение доступа, контроль размера/ошибок и периодическое тестовое восстановление обязательны. JSON не заменяет полный backup.

Восстановление выполняется оператором в maintenance-режиме: остановить writers, проверить backup `integrity_check` и `foreign_key_check`, заменить файл безопасно, очистить старые сессии/lease, изменить dataEpoch, запустить проверку структуры/приложения, затем открыть запись. Старые клиентские команды после restore отклоняются; незавершённые формы не применяются автоматически.

### 19.5. Наблюдаемость и безопасность

`GET /health/live` — процесс жив, без SQL/секретов; `GET /health/ready` — соединение, миграции, режим хранения и базовые права; без бизнес-данных. `GET /api/v1/meta` — API version, schema version, supported frontend contract, capabilities, server time. Подробные sqliteVersion/build доступны admin или оператору.

Следить за p95 API, busy/lock errors, размером базы/WAL, свободным местом, последним успешным backup, конфликтами и ошибками валидации. Не обещать конкретную пропускную способность до теста на выбранном сервере. Переход к PostgreSQL обсуждать при устойчивой конкуренции записи, нескольких серверах или неудовлетворительном времени транзакций, не по одному лишь числу сотрудников.

Обязательны параметризованные запросы, whitelist сортировок/полей, ограничения запросов login, экранирование текстов при HTML-выводе, безопасный CSV, CSRF и server-side authorization на каждом endpoint. Текущий HTML содержит inline scripts: строгий CSP вводить через nonce/hash или вынос скриптов, не ломая страницу слепым запретом и не оставляя `unsafe-eval` как постоянное решение. Без публичной регистрации, без дефолтных паролей, без произвольных URL для серверного скачивания.

## 20. Подключение существующего фронтенда

### 20.1. Репозиторий данных

Ввести `LocalRepository` для явного автономного деморежима и `ApiRepository` для серверного режима. Выбор — настройка сборки/запуска, **не fallback при ошибке сети**. Общие бизнес-модели могут остаться прежними; API DTO преобразуются адаптером в текущую view-model.

| Текущая точка | Серверная замена |
|---|---|
| Чтение STORAGE, `demo()`, `initGoals` | auth → bootstrap → map DTO; демо только явно |
| `save()`, `change(...)` | Не загружать весь `data`; отправлять конкретную команду/API mutation |
| `commitTransfer5` | transfer-preview → подтверждение → transfers |
| `gUpdate`, `saveGoalForm` | create/PATCH/update цели; await успеха перед заменой локальной модели |
| `gAssign` | POST participants, без переназначения owner |
| `c8SaveAssignments` | PUT assignments с ревизией всей цели |
| `c8SaveProduct` | product command и новые люди в одной транзакции |
| `c9Commit`, `c9Save` | API инициатив с revision и едиными ошибками |
| `validateImport5`, import-file | imports preview/commit; исходный JSON сохраняется до завершения |
| `exportJSON`, `c8ExportObject` | согласованный серверный экспорт |
| `history`, `goalUndo` | серверные operation undo-preview/undo |
| `c10View`, карта | чтение проекций; геометрия остаётся в браузере |

После успеха сервер возвращает канонические записи, новую ревизию и operationId; клиент использует их, а не предполагает, что сервер сохранил исходный объект без изменений. При отказе форма не закрывается и не пишет «Сохранено». Повторная отправка кнопкой использует тот же key только пока тело запроса не изменилось.

`localStorage` в серверном режиме хранит лишь настройки отображения и явный экспорт-резерв, сделанный пользователем. Бизнес-кэш не имеет права молча стать источником записи. Несохранённая форма живёт в памяти; после разрыва сети отображается read-only состояние и возможность повторить/скопировать ввод. Браузерный unload-warning не считается гарантией сохранности.

### 20.2. UI, который сохраняется

Три раздела, их цвета и навигация; компактные формы; прогресс вверху цели; поиск сотрудников; единая карточка человека; точки входа из карты; защита несохранённых полей; существующий Гант и презентации. Добавляются только login, текущий пользователь, индикатор серверного сохранения, состояние lease, конфликт и выбор импорта.

Ожидаемые состояния запроса: `loading`, `ready`, `saving`, `saved`, `validationError`, `conflict`, `offline`, `sessionExpired`, `serverError`. Ни одно не должно давать белый экран. `serverError/offline` не скрывают несохранённую форму. При 422 fieldErrors раскрывают нужную секцию, при 409 пользователь видит отличия, при 423 — владельца редактирования и понятный выход.

После подключения API обязательно повторить сценарии v0.11 на реальном HTTP/HTTPS, реальной SQLite и Safari/iPhone. Старые тесты с имитацией `localStorage` не доказывают работоспособность серверного режима.

## 21. Порядок реализации

1. **Основа:** SQL-миграции, конфигурация, первый admin, sessions/CSRF, права, ошибки, idempotency, транзакционный аудит. Проверить restart с сохранением данных.
2. **Структура:** люди/справочники, snapshot read, lease, команды, переносы, продукты, публикация/архив/undo. Проверить граф и сохранение целей отдельно.
3. **Результаты:** цели/назначения/статусы, инициативы/сроки, сводки, Gantt/read snapshots, CSV. Сравнить расчёты с текущим интерфейсом.
4. **Перенос:** импорт v3 через preview/commit, export server-v1, сохранение старого JSON, change-feed, адаптер фронтенда без dual-write.
5. **Выпуск:** реальные интеграционные тесты, два браузера, телефон, backup/restore, проверка блокировок/диска/сессий, HTTPS, ручная приёмка.

Промежуточные этапы — порядок разработки, не урезанный конечный контракт. Перед разработкой HTTP-обработчиков оформить машиночитаемый `openapi.yaml` по этому документу и проверять его в CI. В этом коммите OpenAPI и backend-код не создаются; нельзя выдавать текстовую спецификацию за исполняемый контракт.

## 23. Источники и принятые допущения

Требования и названия сущностей сверены с исходным кодом портала, а не со сторонней системой управления задачами. Архитектура, API, лимиты, роли, аренда, интервалы опроса, политика предупреждений и сроки бэкапов — проектные решения этого документа; до запуска их подтверждает владелец сервиса.

Технические основания:

- **S1.** SQLite, Appropriate Uses: один писатель и границы применения — https://www.sqlite.org/whentouse.html
- **S2.** SQLite, WAL: concurrency, локальный диск, checkpoint, durability — https://www.sqlite.org/wal.html
- **S3.** SQLite, PRAGMA и foreign keys — https://www.sqlite.org/pragma.html и https://www.sqlite.org/foreignkeys.html
- **S4.** SQLite, Online Backup API — https://www.sqlite.org/backup.html
- **S5.** OWASP, Session Management — https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html
- **S6.** OWASP, Password Storage — https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html
- **S7.** OWASP, CSRF Prevention — https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html
- **S8.** Исправление WAL-reset и история релизов — https://www.sqlite.org/releaselog/3_51_3.html и https://www.sqlite.org/changes.html

**Критерий завершённости:** все действующие сценарии портала работают через API из двух независимых браузеров, бизнес-правила enforced сервером, изменения переживают restart, конфликты не теряют данные, старый JSON переносится без молчаливых потерь, backup действительно восстанавливается. Наличие endpoint `/save` с одним большим JSON само по себе этим критериям не соответствует.
