# ClusterBoard API v1 — запуск и целостность данных

**Дата:** 2026-11-09. Дополнение к [основной спецификации backend API](backend-api.md). Оба документа описывают будущую реализацию, не существующий сервер. Эти уточнения закрывают запуск пустой базы, замену набора данных и оставшиеся служебные контракты. При реализации читать вместе с основной спецификацией.

## 1. Первая инициализация без публичной регистрации

Для v1 выбран один кластер на инсталляцию. Не нужен публичный endpoint, позволяющий создавать новые пространства.

Предлагаемая CLI-команда `clusterboard init` (её ещё требуется реализовать):

1. Проверяет схему SQLite и отсутствие уже созданной области. На непустой базе повторный запуск не сбрасывает данные.
2. Запрашивает логин администратора, пароль скрытым вводом, название кластера и IANA timezone. Пароль не передаётся аргументом командной строки и не печатается.
3. В одной транзакции создаёт пользователя, workspace, membership admin, начальные дисциплины/шаблоны, стабильный ID корня и пустую текущую структуру. В current есть только кластер: без людей, продуктов, целей и инициатив.
4. Записывает `workspaces.initialized = 0`, `dataEpoch`, ревизии и событие `workspace.bootstrapped`. Начальная пустая current имеет явную пометку `bootstrap`, чтобы не выдавать её за утверждённую кадровую структуру.
5. Пользователь входит в портал и выбирает «Заполнить структуру» либо «Импортировать JSON». Первый вариант создаёт draft существующим `POST W/structure-versions`; имя кнопки не требует отдельного неописанного API создания workspace.

После первой бизнес-записи или успешного импорта `initialized=1`. Импорт `mode=initialize` разрешён только при `initialized=0`, наличии исключительно bootstrap-root и отсутствии бизнес-данных. Заполнение людей или инициатив уже делает область непустой. Для неё нужен явный `replace`.

Начальная структура с пустыми руководителями не нарушает ссылочную целостность; предупреждения описывают незаполненность. Следующая публикация использует обычную проверку и принятие предупреждений. Создание нового draft после удаления/отбрасывания предыдущего не возвращает `initialized=0`.

`GET /api/v1/workspaces` возвращает только области из membership пользователя: `{items:[{id,name,timezone,revision,dataEpoch,initialized}]}`. В v1 обычно одна. Изменять членство может admin через уже описанные user endpoints. Число рабочих пространств в UI не расширяется этим дополнением.

## 2. Обязательная защита от старого набора данных

Проверки `expectedRevision` недостаточно после полной замены базы: у импортированной записи может случайно оказаться тот же ID и тот же номер ревизии.

Поэтому каждый бизнес-запрос на запись дополнительно содержит:

```http
X-Workspace-Epoch: <dataEpoch from bootstrap>
Idempotency-Key: <operation key>
X-CSRF-Token: <session token>
```

Для структурной записи также нужен `X-Edit-Lease`. Epoch обязателен для создания, PATCH, команд, публикации, подтверждения статуса, отмены, commit импорта и изменения настроек. Для чтения, login/logout/CSRF он не требуется. Получение/продление lease проверяет epoch в теле либо заголовке; в реализации выбрать заголовок единообразно.

Алгоритм проверки внутри транзакции:

1. Убедиться в актуальности аутентификации и прав.
2. Сравнить клиентский epoch с текущим `workspaces.data_epoch`.
3. Только после этого искать завершённый idempotency record текущей области/epoch.
4. Затем проверить ожидаемую ревизию и lease.

Отсутствующий epoch → `428 WORKSPACE_EPOCH_REQUIRED`. Несовпадение → `409 WORKSPACE_REPLACED` с текущим epoch и указанием перечитать bootstrap. Ни команда, ни автоматический retry в новом epoch не выполняются. Клиент сохраняет введённые поля для ручного сравнения, но не перепривязывает их к новому набору данных без решения пользователя.

**Особый случай — повтор commit импорта после потери ответа.** Commit сам меняет epoch. Чтобы клиент мог безопасно получить его результат:

- До изменения epoch сервер записывает в `import_plans` неизменяемую квитанцию: `planId, creatorId, requestHash, sourceEpoch, destinationEpoch, operationId, responseJson`.
- `GET W/imports/{planId}` возвращает admin-инициатору состояние `preview|committed|expired` и несекретную квитанцию.
- При повторном `POST .../commit` с прежним epoch сервер сначала проверяет права, принадлежность plan, точное совпадение idempotency key/requestHash и наличие уже завершённой квитанции. **Только этому завершённому импорту** разрешено вернуть прежний успех через границу epoch, без повторной записи.
- Другой body, другой пользователь, новый ключ или незавершённый plan под это исключение не подпадают.
- Идемпотентность импорта не может перезаписать более новые данные, появившиеся после него.

Квитанции завершённого импорта хранятся минимум 7 суток отдельно от удаляемого staging payload; обычный срок preview остаётся 30 минут. Восстановление физического backup отзывает сессии и меняет epoch до допуска записи; это не HTTP-импорт и не выдаёт старым сессиям исключение.

## 3. Пагинация без скрытых пропусков

Для первого выпуска достаточно cursor-пагинации с инвалидированием при изменении области, без долгоживущих транзакций на несколько HTTP-запросов.

Первый ответ списка содержит `listRevision=workspace.revision`. Курсор защищён от изменения и кодирует workspace, нормализованный фильтр/сортировку, listRevision и последнюю пару `(sortKey,id)`. Каждая страница читается в короткой согласованной транзакции.

Если до следующей страницы workspace revision изменился, сервер возвращает `409 LIST_CHANGED`. Клиент перезапрашивает список, сохраняя открытые несохранённые формы и выбранные ID. Не продолжать с offset так, будто набор не изменился. Для умеренной нагрузки портала это приемлемое упрощение; при частых изменениях можно заменить его серверными read-snapshot токенами без изменения смысла API.

`GET W/changes` использует **другую** семантику: монотонный sequence и epoch, а не listRevision. Новые события не делают старый change cursor конфликтным, пока он не вышел из срока хранения. При постраничном change-feed нельзя перескочить сразу к текущему максимальному sequence.

Карты, Гант, презентационные наборы и экспорт читают весь разрешённый срез за один логически согласованный запрос. Их защитные лимиты должны быть явными; нельзя показать первую страницу как весь кластер.

## 4. Служебные настройки и предпочтения

`GET W/settings` возвращает `{revision,timezone,goalStaleDays:14,limits,initialized}`. `PATCH W/settings` — только admin, `{expectedRevision,changes:{timezone},comment}`. `goalStaleDays=14` в v1 не редактируется, чтобы сохранить текущее поведение целей; период инициатив изменяется отдельным `W/initiative-settings`.

Смена timezone требует комментария: она меняет вычисление today/просрочки на границе суток, но не переписывает даты, timestamps и историю. `workspace.name` — отображаемое имя текущего кластера, синхронизируемое при публикации `cluster.update`; изменение будущего имени не переименовывает текущую область преждевременно.

`GET W/preferences` и `PUT W/preferences` относятся к текущему пользователю. PUT: `{expectedRevision,preferences:{...}}`, cookie/CSRF обязательны. Allowlist: последний раздел, фильтры, выбранный квартал, свернутые группы, масштаб и состояние инспектора. Запрещены бизнес-поля, права, произвольные объекты и большой текст форм. Максимум 64 KiB. Preferences имеют собственную revision и не увеличивают business workspace revision/change-feed. При конфликте preferences пользователь может явно выбрать вариант; потеря настройки отображения не должна блокировать сохранение бизнес-формы.

Служебные heartbeat сессии и lease также не увеличивают бизнес-ревизию. `sessions.last_seen_at` достаточно обновлять с ограничением частоты, например не чаще раза в минуту, с учётом допуска по idle timeout; не нужно создавать запись на каждое движение карты.

## 5. Дополнение к модели SQLite

К логической схеме основной спецификации добавить:

- `workspaces.initialized INTEGER NOT NULL DEFAULT 0 CHECK (initialized IN (0,1))`.
- `structure_versions.archived_directory_snapshot_json TEXT NULL` для отдельной фиксации подписей на момент замены текущей версии. Опубликованный `directory_snapshot_json` не перезаписывать.
- `structure_versions.origin TEXT NOT NULL`, значения `bootstrap`, `created`, `imported`, `restored`.
- Поля квитанции завершённого импорта из раздела 2 в `import_plans` либо отдельной `import_receipts`, с уникальностью `(workspace_id,plan_id)`.
- `user_preferences.revision`, если ORM не создал её из общей таблицы модели.

Сущности пользователей/людей не смешиваются. Для `workspace_members` использовать membership revision при изменении роли, а при изменении общих полей user — user revision. Если один запрос изменяет оба набора, он обязан содержать `expectedUserRevision` и `expectedMembershipRevision` и записываться одной транзакцией. Упрощённое `expectedRevision` из основной таблицы user endpoints допустимо только для изменения одного конкретного агрегата; UI должен явно понимать, какой именно редактирует.

Для паролей request hash идемпотентности не сохраняет открытый пароль и не должен служить быстрым офлайн-проверочным хешем пароля. Парольные операции использовать через готовый auth-сервис; для replay хранить только идентификатор операции/несекретную квитанцию. Password hash Argon2id хранится исключительно в users, не в аудите или ответах.

## 6. Уточнения предварительных просмотров

Для transfer/publish/undo preview не нужен новый бизнес-объект, но нужен защищённый от подмены plan. Допустим серверный staging либо подписанный сервером ограниченный токен. В plan входят все влияющие IDs, ревизии, dataEpoch, пользователь, срок и хеш нормализованного запроса. На commit сервер не доверяет рассчитанным клиентом процентам/managerId и повторно проверяет инварианты.

Если body preview не сохраняется в базе, токен не должен раскрывать секреты или персональные данные в URL. Передавать его только в JSON body. Получение preview не увеличивает бизнес-ревизию и не создаёт audit-событие изменения; commit создаёт одно.

Настройки демонабора: `POST W/demo-data/preview` принимает `{expectedWorkspaceRevision,datasets:["structure","goals","initiatives"]}`. По умолчанию disabled. Структурный демонабор разрешён только в пустой bootstrap-области; не добавлять его в действующую current в обход публикации. Демо-цели/инициативы используют существующие IDs лишь после явного предпросмотра связей. Commit принимает planId и подтверждение; ошибка не оставляет частичный набор. Удаление демоданных — тоже preview/commit с проверкой ссылок; нельзя удалить человека, уже участвующего в реальной цели.

## 7. Дополнительная приёмка

| ID | Сценарий | Результат |
|---|---|---|
| BOOT-01 | Повтор CLI init на действующей базе | Ничего не удалено, понятное сообщение |
| BOOT-02 | Первая авторизация | Пустая область без вымышленных сотрудников, доступны импорт/план |
| EPOCH-01 | Старый телефон пишет после replace; ID/revision случайно совпали | 409 WORKSPACE_REPLACED, данных не коснулся |
| EPOCH-02 | Успешный import commit потерял ответ | Повтор возвращает квитанцию, повторной замены нет |
| EPOCH-03 | Чужой пользователь или другое тело повторяет квитанцию | Отклонено |
| PAGE-01 | Область изменилась между страницами списка | LIST_CHANGED; нет скрытых пропусков/дублей |
| PAGE-02 | Событий change-feed больше лимита страницы | Все события выданы последовательно |
| PREF-01 | Изменяется масштаб/предпочтение | Не инвалидирует чужую бизнес-форму |
| USER-01 | Меняются роль и профиль одновременно | Проверены обе ревизии, атомарный commit |
| DEMO-01 | Демо включено на непустой области | Структура не заменяется и не дополняется без разрешённого сценария |

Эти проверки дополняют, а не заменяют основной набор. Ни одна из них не объявляется пройденной до появления работающего сервера.
